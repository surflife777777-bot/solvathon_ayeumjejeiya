대다수의 사람들이 학교생활 중 매점의 자신이 원하는 음식이 없거나 품절 되는 경우가 있어 불편함을 느낌 

상황: 평소에 즐겨먹는 빵이 있는데 매점에서 팔지 않아서 불편함 
     체육시간에 한라봉 에이드를 먹고싶어서 매점에 갔지만 없어서 영어 수업시간에 지각을함 

근거: 7반학생에게 물어본 결과 체육시간이 끝나고 매점에 갔는데 물건이 품절되어 있어 시간을 낭을함
     5반 친구들에게 물어본 결과 원하는 간식이 매점에 들어오지않아서 불편함

## 2. 해결
핵심 시나리오:김XX가 M-run에 지금 재고로  들어가서 매점에 무슨음식이 있는지 확인한다.—> 먹고 싶은 간식에서 본인이 원하는 간식을 쓰고 요청한다. —-> 김xx가 올린 간식을 보고 다른학생들이 찬성이나 반대 투표를 한다.

| 구분 | 기능 |
| --- | --- |
| 필수 (15:30까지 반드시) |지금 재고종류(아이스크림,과자,음료, 빵,기타),재고 가격,재고 개수,간식이름으로 찾기 검색칸,먹고 싶은 간식 요청(간식이름,한마디)  |
| 선택 (시간이 남으면) |새로고침|
| 제외 (오늘 하지 않음) | 타학교 운영가능하게 하기,운영자 사용하는 기능(타학교승인,관리자 비번 변경) |

- [X] 재고 가격

## 3. 설계

<!--
쓸 것: 화면 흐름 / 데이터 구조 / 기술 선택과 이유
- 화면 흐름: 화면 이름 3~5개를 화살표로 잇습니다.
- 데이터 구조: 저장할 대상과 항목을 코드 블록으로 씁니다.

  "막히면 무엇으로 바꾸는지"(대안)까지 쓰면 설계 점수의 근거가 됩니다.
평가 연결: 논리적 설계 역량
-->

**화면 흐름:** 학교 계정 로그인 → 재고 확인 → 먹고 싶은 간식 요청 후 투표 → 재고 수정, 간식 선

**데이터 구조:**

```
상품(items): id, 이름, 분류, 가격, 재고 수, 바코드, 수정 시각
간식 요청(wishes): id, 간식 이름, 비교용 이름, 한마디, 요청자 id, 요청자 이메일, 선택 여부, 숨김 여부, 요청 시각
투표(votes): 요청 id, 투표자 id, 값(찬성 +1 / 반대 -1), 투표 시각   ← (요청 id + 투표자 id)가 기본키라 1인 1표
계정(구글 로그인): 이메일   ← 역할은 저장하지 않고 이메일 규칙으로 판별 (숫자와 -만 = 학생, 영어 포함 = 선생님, 지정 주소 = 관리자)
```

**기술 선택:**
선택: HTML/CSS/JavaScript 한 파일 + Supabase(데이터베이스·로그인), Netlify로 배포
이유: 전교생이 같은 재고와 투표를 봐야 해서 서버가 꼭 필요하다. Supabase는 DB, 로그인, 보안 규칙을 한 곳에서 제공하고 무료다. 화면은 빌드 없이 파일 하나로 두어 수정하고 다시 올리기 쉽게 했다.
고르지 않은 안: 브라우저 저장소(localStorage)만 쓰는 방식. 설정 없이 바로 되지만 데이터가 각자의 폰에만 저장되어, 투표를 모은다는 목적을 이룰 수 없다.
보완: 서버 연결에 실패하면 화면 위에 원인(키 오류, 표 없음, 인터넷 차단)을 구체적으로 띄워서 어디서 막혔는지 바로 찾을 수 있게 했다.
막히면 / 다음 단계: 데이터 저장 코드를 ServerBackend와 LocalBackend 두 곳에 같은 함수 모양으로 모아 두었다. CONFIG의 서버 주소만 비우면 localStorage 버전으로 바로 돌아가고, Firebase로 바꿀 때도 저장소 한 곳만 교체하면 된다.
